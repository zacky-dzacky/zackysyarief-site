Every few months I try to look up from the tools I use daily and ask what the research is actually saying. This time I went through the ICML 2026 program, the agent papers that landed on arXiv between May and August, the JetBrains and Pragmatic Engineer developer surveys, METR's time-horizon update, and a handful of security studies.

I am not a researcher. I am a software engineer who has worked across the stack. On the side I build RAG and agent things ([Caridata](/blog/caridata-hybrid-rag), [Kalee Harness](/blog/kalee-harness), [MCP with Google ADK](/blog/connect-mcp-using-google-adk)). So this is a working engineer's read, filtered through that experience. Where a number comes from a vendor report rather than a peer-reviewed paper, I say so.

Six trends came out of it. Here they are at a glance, then one section each.

| # | Trend | Strongest evidence | What it changes for me |
| --- | --- | --- | --- |
| 1 | The job is becoming orchestration, and the delegation gap is the problem | 90% of devs use agents weekly; only 0–20% of tasks fully delegated; METR horizons doubling every ~3–4 months | How I split work, not which model I pick |
| 2 | Verification, not generation, is the bottleneck | Verification Horizon paper; Veracode secure-output rate flat at 55% | Where I invest: tests, monitors, verifiers |
| 3 | Leaderboards are being replaced by trajectory evaluation | AgentAtlas; "Coding benchmarks are misaligned" position paper | How I pick and trust a model |
| 4 | Context engineering and memory are the real design surface | Memory-as-Action, InfiAgent, SWE-ContextBench | How I structure repos and agent sessions |
| 5 | The attack surface moved into the tool result | MCP tool poisoning; PR-title injection that leaked CI secrets | How I sandbox and permission agents |
| 6 | Small models are now a workload you can own and deploy | Gemma "E" models, Qwen 0.8B–9B, ~1 GB 4B models on phones and single-node servers | What I can self-host, and what I can ship on-device |

# 1. Orchestration is the job now, and the delegation gap is the problem

The adoption numbers stopped being interesting because they are no longer in doubt. JetBrains surveyed more than 15,000 professional developers between May and July 2026: 90% use AI coding agents at work at least weekly, 68% daily. Claude Code went from 18% workplace adoption in January to 39% by mid-year. The Pragmatic Engineer survey (906 respondents, early 2026) found that 55% regularly use agents and that Staff+ engineers use them more than anyone else, at 63.5%.

**My read.** Agent capability is now measured in workdays and my review capacity is still measured in minutes. That mismatch is the delegation gap. It is not a model problem. It is a task-decomposition problem, and I have written about that before, from the human side, in [why adding more developers doesn't shorten your timeline](/blog/sofware-development-timeline-factors). Brooks's law applies to agents too: the cost of a parallel worker is the coordination overhead it creates for whoever integrates the output. Anthropic's own multi-agent research system is the canonical case study here: a lead agent decomposes the job, specialist sub-agents work in parallel on a shared filesystem, and results flow back to one context that owns the merge. When I built Kalee Harness, the sub-agent handoff was the single hardest layer to get right, and for exactly this reason.

**What I am doing.**

- Classifying tasks by *verifiability* before delegating them, not by difficulty. A hard backend change with a good integration suite is more delegable than a trivial one with none. A Terraform change with `plan` output is more delegable than a hand-applied config change.
- Measuring my own delegation rate. If I cannot say what fraction of last week's tickets an agent finished unattended, I cannot improve it.
- Writing task specs as if for a new joiner, with acceptance criteria, because that is what an orchestrator does.
- Giving agents the same fast, reproducible environment I would give a new engineer: containerised, seeded, one command to run the tests. Long-horizon runs are only as good as the loop they can execute inside.

# 2. Verification, not generation, is the bottleneck

Two very different sources landed on the same conclusion this year.

The first is a training paper, *The Verification Horizon* (arXiv 2606.26300). Its claim: for coding agents, generating candidate solutions is no longer the hard part. Reliably verifying them is. No static reward function survives contact with a stronger policy, because the policy finds the loophole. Their fix is to make verifiers co-evolve: behaviour monitors, quality judges, and interactive evaluators layered on top of unit tests. On software-engineering tasks, adding a behaviour monitor cut exploitative solutions from 29% to 1%, and monitoring plus filtering raised clean task success from 40% to 61%. Their conclusion is the one to remember: *every verifier is only a proxy for human intent.*

The second source is Veracode's longitudinal security study, now covering more than 150 models. Across all models and tasks, only about 55% of generation tasks produce secure code. That number was 55% in 2025 and it was still 55% in March 2026, a period during which coding benchmarks like HumanEval kept climbing. Their earlier report put AI-generated code at 2.74x the vulnerability rate of human code, with cross-site scripting missed in 86% of relevant samples. GitClear's repository data shows the quality side of the same story: copy/paste rates up from 8.3% (2021) to 12.3% (2024), refactoring down from ~24% to under 10%.

There is also a provocative position paper, *The End of Code Review: Coding Agents Supersede Human Inspection* (Monperrus, 2606.13175), arguing that agents can now replace human review in some workflows. I read it as a useful overstatement. Its own limitations section admits the evidence is benchmark-based, and that review does things other than catching bugs, like spreading knowledge across a team.

**My read.** This is the trend I have the most direct experience with. Kalee Harness exists because a one-pass model review is a bad review. It runs a scan pass and then a separate verify pass, and every finding is labelled `CONFIRMED` or `PLAUSIBLE`, because a reviewer that cannot say how sure it is has not finished its job. That design was intuition when I built it. The Verification Horizon paper is the same idea with numbers attached. The devops version of the same lesson: a pipeline that only runs unit tests is a static verifier, and an agent will happily produce code that passes it and still breaks the deploy. And in a bank, where a missed injection flaw is a regulatory event and not just a bug, the flat 55% line is the chart I would show a manager who thinks review is now optional.

**What I am doing.**

- Treating verifiers as first-class code. Tests, linters, SAST, dependency scanners, and `terraform plan` are now tools the agent *calls*, not a gate it hits afterwards.
- Adding a behaviour monitor to any agent that edits code or infrastructure: a second model whose only question is "did the first one do something it should not have?"
- Making the pipeline the verifier of record: contract tests against real service interfaces, ephemeral preview environments per PR, and a smoke test that runs before a human ever opens the diff.
- Keeping the `CONFIRMED` / `PLAUSIBLE` split in review output, and treating prompt changes as falsifiable experiments against a fixed set of known-bad diffs.

# 3. Leaderboards are being replaced by trajectory evaluation

A position paper from June (*Coding Benchmarks Are Misaligned with Agentic Software Engineering*, 2606.17799) says out loud what most of us noticed in practice: SWE-bench-style benchmarks score a single, isolated fix, while real agentic work is iterative, tool-heavy, and collaborative. High scores do not reliably predict effectiveness in a real repository.

The constructive response is a wave of new evaluation work. AgentAtlas (2605.20530) proposes judging *trajectories*, not outcomes, with a six-state control taxonomy: Act, Ask, Refuse, Stop, Confirm, Recover. Two of their findings matter to practitioners. First, no single model dominates all axes; the strongest model on control decisions was the weakest on tool-context use. Second, when the taxonomy is removed from the prompt, trajectory accuracy drops 14–40 points and every model family compresses to 0.54–0.62. Explicit structure in the prompt inflates apparent capability. Alongside it, Dialogue SWE-Bench and SWE-Together test agents in multi-turn sessions with a user, SWE-EVO tests long-horizon software evolution, and SWE-ContextBench (1,476 tasks, 51 repositories, 9 languages) tests whether an agent can *reuse* experience from earlier tasks.

| What an outcome score tells you | What a trajectory tells you |
| --- | --- |
| The tests passed | Whether it asked when the spec was ambiguous |
| — | Whether it stopped when the task was done, or kept going |
| — | Whether it took an unsafe path to a correct answer |
| — | How many tokens and tool calls it burned |
| — | Whether it recovered from a failed tool call or looped |

**My read.** I picked models for Kalee Harness with a conformance suite, not a leaderboard, because the leaderboard told me nothing about whether a local 8B model would stop calling tools once it had the answer. With local models the Ask/Stop/Recover behaviours were the whole ballgame. AgentAtlas gives that a vocabulary. The practical takeaway is that the model ranking you should care about is the one on *your* tasks, in *your* harness.

**What I am doing.**

- Keeping a 20–30 task eval set pulled from real tickets in my own repos, with expected outcomes, and re-running it whenever a model or prompt changes.
- Logging full trajectories (tool calls, tokens, cost), not just pass/fail. Kalee prints token and cost accounting per run for this reason.
- Scoring Ask/Stop/Recover explicitly when comparing models, especially open-weight ones.

# 4. Context engineering and memory are the design surface

The most crowded corner of the summer's arXiv was agent memory: *Memory as Action* (autonomous context curation for long-horizon tasks), *InfiAgent* (bounded reasoning context with persistent state externalised to files), *CoMem* (context management with a decoupled long-context model), *SAM* (state-adaptive memory), a proactive memory agent, and at least one full survey. The shared premise is that a bigger context window does not solve long-horizon work; deliberately curating what is in the window does.

The theme is not new to anyone who has built RAG. It *is* new that the same discipline is now being applied to the agent's own working state, and that file-centric state (write it down, read it back) keeps beating clever in-context tricks.

**My read.** Caridata is context engineering for documents: hybrid dense + SPLADE retrieval with RRF fusion exists because dense-only retrieval put the wrong passages in the window. An agent's memory has the identical failure mode, and the identical fix: retrieve selectively, keep the window bounded, write durable state to disk. The other lesson is in the papers' architecture choices. InfiAgent's file-centric state is exactly what a `CLAUDE.md`, a `memory/` directory, or a session log is. When I added sessions to Kalee, they came *after* the harness worked stateless, and I think that ordering was right: make the loop correct, then decide what deserves to persist.

**What I am doing.**

- Writing repository memory files (architecture notes, conventions, known traps, how to run the service locally, what the deploy pipeline expects) as deliberately as I write tests, and reviewing them in PRs.
- Making runtime context retrievable, not just code context. An agent debugging a production incident needs logs, traces, and dashboards as tools it can query, scoped to the incident window, instead of a screenshot pasted into the prompt.
- Treating the context window as a budget with a bill attached, the same way I estimated GPU memory in [the foundation-model GPU post](/blog/calculate_and_estimate_gpu_usage). Every sub-agent is a fresh window; that is the cost of parallelism.
- Trying experience reuse deliberately: give the agent the trajectory of the last similar task and measure whether it helps or just adds noise.

# 5. The attack surface moved into the tool result

This is the trend I would put at the top if I were ranking by consequence.

The security literature on MCP consolidated this year into a taxonomy: tool poisoning (instructions hidden in tool descriptions), rug pulls (a server silently redefining a tool after approval), tool shadowing, cross-server attacks, confused-deputy OAuth flows, and the "lethal trifecta" of private data access, untrusted content, and an exfiltration channel in one agent. A 2026 study of seven MCP clients found tool poisoning the most prevalent client-side vulnerability, mostly because clients do not statically validate tool descriptions or show users the parameter values being sent.

Then in April 2026 a Johns Hopkins team demonstrated the real-world version. They put instructions in GitHub pull request *titles*. Claude Code, Gemini CLI, and GitHub Copilot read the PR data as part of an ordinary task, followed the injected instructions, and exfiltrated GitHub Actions secrets. The injection did not come from a user. It came from a tool result.

A separate study (*Are AI-assisted Development Tools Immune to Prompt Injection?*, 2603.21642) tested seven tools against four attacks via poisoned tool metadata:

| Tool | Safe | Partial | Unsafe |
| --- | --- | --- | --- |
| Claude Desktop | 3/4 | 1/4 | 0/4 |
| Claude Code | 3/4 | 1/4 | 0/4 |
| Continue | 3/4 | 1/4 | 0/4 |
| Cline | 2/4 | 0/4 | 1/4 |
| Gemini CLI | 2/4 | 2/4 | 0/4 |
| Langflow | 1/4 | 3/4 | 0/4 |
| Cursor | 0/4 | 0/4 | 4/4 |

The attacks were reading `~/.ssh`, logging every tool invocation, generating phishing links, and executing a remote script. None of them required the user to type anything unusual.

**My read.** Every layer of the stack I have worked on already learned this lesson once. On the backend it is "never trust the request body"; on the client it is [OWASP for Android developers](/blog/owasp-things_android_developer_should_know) and [countering reverse engineering](/blog/9-strategies-to-counter-android-re), where an intent, a deep link, a WebView message is hostile until proven otherwise; in devops it is the supply chain, where a dependency or a CI action is code you are choosing to run. For an agent, *every tool result is hostile input*. The PR title, the web page, the Notion doc, the JSON from an MCP server. And the PR-title incident is specifically a devops story: the agent ran inside CI with a token that could read secrets, which is the same blast radius as a compromised GitHub Action. Anthropic's own trends report says agents help defenders and attackers scale equally, and I believe it. In a banking environment an agent with a production database tool and a browser tool is the lethal trifecta by construction. Kalee Harness has no edit tool and only read-only tools on purpose. That was a design simplification when I made it; today I would call it the security model.

**What I am doing.**

- Least privilege per agent, enforced by the harness, not the prompt. Review agents get read-only tools. Editing agents get no network. Nothing that runs in CI gets a token broader than the job needs.
- Treating MCP servers like dependencies: pinned, reviewed, and with tool descriptions diffed on update to catch rug pulls. Same policy I already apply to GitHub Actions and base images.
- No auto-approve anywhere near CI credentials. If an agent runs in a pipeline, it runs in a container with scoped, short-lived tokens, egress restricted, and an audit log.
- Building the "did this task's inputs contain instructions?" check into the behaviour monitor from trend 2.

# 6. Small models are now a workload you can own and deploy

The last trend is quieter and, for anyone who runs their own infrastructure, maybe the most useful. As of mid-2026 small language models are a realistic workload on hardware you control, whether that is a phone, a single GPU box in your own rack, or a modest cloud instance. Google's Gemma "E" variants use per-layer embeddings to cut runtime memory well below what the parameter count implies, and are the reference targets for the LiteRT-LM on-device stack. Alibaba shipped a Qwen small series from 0.8B to 9B parameters, explicitly spanning IoT devices up to local servers with one family. Microsoft's Phi line keeps showing that data quality substitutes for size. Quantised to 4 bits, a capable ~4B model is about a gigabyte: it runs on a phone, a Raspberry Pi 5, or, more relevant to a backend team, dozens of concurrent requests on one mid-range GPU. Vendor reports claim a large share of enterprise deployments now run local SLMs for sensitive data; I would treat the exact percentages with caution, but the direction matches what I see.

**My read.** This is now a deployment decision, not a research question, and it is one backend and platform engineers are well placed to make. Caridata is the small-scale version: `embeddinggemma` and a local Ollama generator behind a FastAPI service, Qdrant for retrieval, everything on a box I own, and no document ever leaving it. That architecture is the pattern: a model becomes one more stateless service with a health check, a resource limit, and a place in the deploy pipeline, and the [GPU-memory arithmetic](/blog/calculate_and_estimate_gpu_usage) becomes ordinary capacity planning. The trade-off is the same one as any self-hosted dependency, operational burden in exchange for control over data, latency, and cost. Then there is the on-device end of the same spectrum, which I wrote about in [Language User Interface](/blog/language-user-interface) and [cosine similarity with SQLite + EmbeddingGemma](/blog/cosine-similarity-from-scratch): for a banking app, transaction categorisation or document Q&A over statements without the data leaving the phone is sometimes the only way the feature is allowed to exist at all.

**What I am doing.**

- Running one small model as a proper service: containerised, with a health endpoint, resource limits, structured logs, and a load test, so the team can treat it like any other backend dependency.
- Measuring the real numbers before choosing: tokens per second per GPU, p95 latency under concurrency, and cost per thousand requests versus a hosted API for the same task.
- Prototyping one on-device feature end to end with EmbeddingGemma plus a ~1B–4B generator, benchmarked on a mid-range device, not the flagship in my pocket.
- Being honest about the boundary: self-hosted or on-device for private, latency-sensitive, bounded tasks; hosted frontier models for everything that needs their reasoning.

# Challenges, and what I plan to do about them

| Challenge | Why it bites | Mitigation |
| --- | --- | --- |
| Review capacity does not scale with agent output | A 16-hour agent run produces more diff than I can read | Delegate by verifiability; require tests with every agent PR; verify with a second agent before I look |
| Verifiers get gamed | Every verifier is a proxy; strong models find the gap | Layer monitors; rotate and re-check verifiers; keep a set of known-bad cases |
| Enterprise procurement lag | The Pragmatic Engineer data shows big companies default to whatever is bundled | Run the eval set on the tools I *can* use; make the case with numbers from my own repos |
| Prompt injection has no clean fix | Defences are improving, none are complete | Assume compromise: least privilege, sandbox, scoped tokens, audit log |
| Local models underperform on Ask/Stop behaviours | Open-weight models loop or over-act more | Conformance suite before adoption; keep them on bounded, read-only tasks |
| Regulated environment | Banking cannot ship what it cannot explain | Trajectory logs and per-run cost accounting are the audit trail |
| Agents in CI and production | An agent with a deploy token is a new privileged principal | Short-lived scoped tokens, egress restrictions, separate identity per agent, same review as a new service account |
| Operational cost of self-hosting models | One more GPU service to page on | Run it like any other service: SLOs, resource limits, load tests, a fallback to a hosted API |
| Skill drift | If agents write all the code, does anyone still understand it? | Keep humans on architecture and review; rotate who reads the agent's trajectories |

1. Build a 25-task eval from real tickets and run it against every tool I use. Score outcome *and* Ask/Stop/Recover.
2. Add a behaviour-monitor pass to Kalee, and re-measure the false-positive rate on the known-bad set.
